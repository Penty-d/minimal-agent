# 架构设计题答题记录

## 模块一：Context / Performance

**1. 大模型面对第一轮长窗口或多模态输入时，first token 会显著变慢。有什么快速/低成本/用户体验也不差的方案？从5-10秒稳定压缩到2秒。**

尽可能维持前缀稳定，prefill因为计算复杂度高所以速度慢，因此尽可能保持前缀稳定，这样不用频繁prefill，首字速度就会提高，如果是多模态图片，第一轮可以考虑用缩略图加快时间，避免图片编码过慢。

## 模块二：Memory

**1. 和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？**

用纯文本保存memory，模型提取摘要后存入本地memory，并做一个简单去重，然后再对所有memory做一次摘要，将总摘要内容放入system prompt之后，提供一个读取具体memory信息的tool，如果模型需要可以做一个tool call来决定是否召回详细信息。

## 模块三：Task

**1. 对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？**

由于对话轮次长了以后，context变大导致模型注意力稀疏，因此可能偏移目标，我个人想法是，首先在压缩上下文时提取并保留用户目标，做成一个todo或者goal；或者引入当下流行的subagent，将任务分配给subagent执行，这样主模型可以保持更久的目标记忆，同时也可以引入judge agent，为长期执行的任务适时做判断，及时纠正任务执行方向。

**优缺点方面：**
- Todo 看板实现简单但复杂任务不够用；
- Subagent 可以很好的隔离上下文，但通信调度开销大；
- Judge Agent 能主动纠偏但多耗费 Token 和时间。

## 模块四：Tool / Session Runtime

**1. Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？**

设计一个任务流，在模型开始执行异步任务时给一个taskid，同时告知用户后台任务正在运行，此时允许可以接受用户的消息，同时后台跑异步任务，在任务结束后，通过taskid将执行结果插回context，并告知用户已经完成。

## 模块五：Agent Runtime 架构对比

**1. Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？**

Claude Code 用的是内容块流式协议，工具调用、思考过程和普通文本放在同一个有序的 content 列表里，原生支持交替输出，而且对于大段代码或终端命令，不需要在 JSON 字符串里做繁琐的反斜杠转义。 OpenAI 兼容协议是把 tool_calls 单独作为一个字段和 content 分开，工具参数arguments是一个整段的 JSON 字符串，工具结果还需要用专门的 tool 回喂。

**优缺点方面：**
- **OpenAI 兼容方案**：优点是生态通用性好，国内外模型和开源库大多默认兼容；缺点是大段代码转义开销大，容易出现 JSON 格式解析错误，且流式传输时必须等整个 arguments 拼接完成才能反序列化。
- **Claude 方案**：优点是天然支持思考、自然语言与多工具调用的原生交错生成，流式响应更快，非常契合代码开发类 Agent；缺点是协议相对私有，接入其他大模型时需要额外写适配层。
